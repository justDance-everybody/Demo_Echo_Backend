# 工程笔记：实测明细、边界与录屏细节

README 只放结论，这里放支撑结论的明细和目前已知的边界。数据来自 2026-11-24 对 `qwen3.8-omni-flash-realtime`（阿里云百炼北京地域）的测试。

## 意图评测

命令：`uv run python eval/run.py --repeat 3`。13 条用例（`eval/cases.yaml`）各跑 3 轮，共 39 次。每次新开一个会话，用文字输入，所以结果不含语音识别误差。写操作只会走到“待确认”，评测不替用户确认，不会真的执行。

两个口径：

- **任务办成**：调用了期望的工具且参数匹配；或者用例写了 `reply_any`（目前只有两条算术题），模型没调工具但回答里出现了正确结果。
- **第一步就选对工具**：第一个非确认类的工具调用就是期望的那个；期望不调工具的用例，没调就算对。

| 用例 | 期望工具 | 办成 | 第一步选对 | 首字延迟中位数 |
|---|---|---|---|---|
| 现在几点了 | `get_time` | 3/3 | 3/3 | 1.53 s |
| 今天星期几 | `get_time` | 3/3 | 3/3 | 1.51 s |

## 真语音测试

评测用文字输入，语音链路另外测：

- **演示录屏**：用 `demo/record.sh` 和同一套脚本录了多条完整流程（查天气、记备忘并口头确认、中途打断）。
- **单独重复**：把“记备忘”和“好的，记吧”两段语音按实时速率直接灌进模型连接，不经过浏览器，重复 6 次。

### 确认闸相关

把 VAD 换成 `semantic_vad_ec` 之后，“记备忘 → 用户说好”一共走了 13 次（7 条完整录音 + 6 次单独重复）：

- 12 次正常：模型调用 `confirm_action`，服务端执行，模型再说“记好了”。
- 1 次异常：模型只说了“这就给你记上”，没有调用 `confirm_action`。服务端因此没有执行，确认闸没有被绕过，但模型说了没做的事。

之后在系统提示里加了一条：用户同意后先调用 `confirm_action`，拿到执行结果之后才能说“记好了”“办好了”。改完以后录的 4 条都正常。这依赖模型遵守指令，服务端保证不了。

换 VAD 之前，用 `semantic_vad` 录的第一条里，模型完全没收到“好的，记吧”这一轮，确认卡住，详见 README 的实测数据一节。

### 打断

演示录音里，用户开口后约 0.6 到 1.1 s 之间 Echo 停止播放（按录屏逐帧判断）。停播依赖模型侧 VAD 发出 `speech_started` 的时机。

### 语音识别和断句

- 偶有错字：一次把“好的，记吧”识别成“好的，去吧”，模型仍理解为同意。
- 句中停顿较长时会被切成两轮：一次把“详细给我讲讲武汉有哪些好吃的，每样都说说”切成了两句，模型先回了一个字，随后按完整意思回答。

## 确认闸的边界

服务端保证的：

- 写工具第一次被调用时不执行，只登记参数。
- `confirm_action` 只在登记之后用户又说过话时有效，模型在用户开口前自行确认会被拒绝（`tests/test_e2e.py::test_model_cannot_confirm_on_users_behalf`）。
- 执行的是登记时的参数，确认时模型传的新参数被忽略（`tests/test_confirm.py::test_confirm_ignores_new_args`）。
- 待确认动作 120 s 过期；前端没有任何直接执行工具的接口。

服务端不判断的：

- 用户那句话的意思。用户说了话之后，是同意还是拒绝由模型理解，再由模型决定调用 `confirm_action` 还是 `cancel_action`。如果模型把拒绝误判成同意，或者语音识别把“不”听丢了，写操作仍会执行。
- 涉及资金这类不可逆操作时，建议在此基础上加一层服务端校验，例如检查用户最后一句的识别文本是否明确表示同意，并配合金额上限、收款方白名单。这部分目前没有实现。

## 已知限制汇总

- 评测集只有 13 条文字用例，没有成规模的语音评测集。
- 首字延迟在一台服务器上测得，受网络位置影响；查天气的延迟主要来自外部 API。
- 远程 MCP 每次调用都新建连接，多一次握手开销；换来的是不保存会话状态、不用处理重连。

## 录屏怎么做的

`demo/record.sh` 在 Linux 上一条命令完成：

1. 用 DashScope `qwen3-tts-flash` 把“用户”一方的台词合成成语音（`demo/tts.py`）。视频里用户的声音是合成语音，不是真人。
2. 起一个独立的 PulseAudio，建三个虚拟设备：Chrome 的扬声器、Chrome 的麦克风、混音。台词用 `paplay` 播进虚拟麦克风，对 Chrome 来说和真人对着麦克风说话一样。
3. 起 Xvfb 虚拟屏幕和 Echo 服务，用 Playwright 驱动真 Chrome 打开网页、点“开始说话”，每句台词等 Echo 说完再播下一句；打断那一步在 Echo 开口 4 s 后插话（`demo/drive.py`）。
4. 屏幕和混音进同一个 ffmpeg，用墙钟时间戳对齐。
5. `demo/compose.py` 加片头片尾和说明框，对话部分不剪，按每句台词的开始时间放说明框，另出 2 倍速 GIF。

README 里的视频是录了多条完整流程后选的一条，对话和服务端行为都是原样，没有剪辑。
